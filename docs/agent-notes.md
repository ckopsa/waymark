## The owner's rulings on the product

### project-narrative-the-feed

THE PROJECT'S FINAL FORM (owner's ruling, 2026-08-27): a Twitter-like feed is the product; everything else serves it. Layer 1 aggregates the owner's digital life (messages, email, chores, meals, people, events, media) under one policy engine. Layer 2 derives OUTCOMES from that data plus declared VALUES: each feed post is one potentially desirable outcome, its PIECES are prefilled calls on any waymark door (jfv.9), and the owner does a piece, skips it, or comments why. Layer 3 learns: taps/declines/verdict words are direct rank inputs; a comment (remark) is raw signal that an agent must INDEX into an insight before the system can learn from it. Canonical story: composer finds son's birthday from contacts/messages, stages 'Celebrate' with 'add to calendar' + 'notify family Telegram' pieces; owner replies 'rescheduling, Wellesley is sick'; next sitting writes the fact as an insight, stages 'Tend to sick wife', and notes the deferral on the birthday outcome. RANKING RULING: an agent authors the judgment (ranking_note score + sentence), never the order; the order is the declared crown rank formula (asked-for first, judged, declared-value, :early, cooled, declined-by-word, fresh), owner feedback enters DIRECTLY not via an interpreter, and agents change weights only through recipe_proposal the owner applies. The engine already has this shape — the gap is narrative (README/spec framing), not code.

### iterate-on-outcomes-is-the-core-loop

THE MISSING CORE PRIMITIVE (owner, 2026-08-27): the feed needs a way to say 'this OUTCOME is good, but the plan/pieces are wrong — I want to iterate on it WITH the AI', distinct from accept (make_it_so), decline (not_this_week, which cools and returns 'next week'), and expire. Today an outcome's only verbs are those three; there is no 'workshop/revise/iterate' gesture, so a comment that critiques the PLAN of a still-good outcome has nowhere to land — the composer can only reply and defer, because supersedes requires the prior to be DECLINED first and the crown rank reads no remark/insight. This iteration loop IS the project's core vision ('over time we tune the STEPS of those outcomes toward what I love doing', see [[project-narrative-the-feed]]): the thread on an outcome is the workshop, the person critiques, the composer REVISES THE PIECES IN PLACE (not a competing twin, not a decline), converging over turns. Shape: (1) a person verb 'iterate/workshop' on an outcome or piece that keeps the outcome and opens a revision; (2) the composer able to replace/re-time pieces of a STANDING outcome it was asked to rework; (3) the thread (waymark-b4s) driving it. The church-at-9 remark (2026-08-27) was the first turn of this and had nowhere to go.

### no-floor-advance-one-arrival

THE COMPOSER LOOP, REDESIGNED (owner's ruling, 2026-08-27, supersedes [[sitting-floor-one-new-outcome]]): the FLOOR is retracted. 'Surface one new outcome every sitting' rewarded quantity, so at a 96/day cadence the fleet padded — single-task 'Prioritize X' wrapper-outcomes, self-made twins, incoherent bundles, and the banned 'mark as done' piece all reappeared (observed 2026-08-27). Owner's diagnosis: a vague objective is gamed (the agent does the minimal thing that passes), and attention-as-reward is too slow/expensive to tune. THE FIX is specification, not incentive: (1) NO floor — a quiet run is a lawful no-op again. (2) EVENT-DRIVEN, evidence-scoped: a run processes concrete ARRIVALS (new tasks, remarks, Gate email/chat) diffed since the last snapshot, not a vague 'find something'. (3) The minimum contribution is ENRICHMENT, below the feed: given a driver-detected BARE task (thin title, no detail/due/linked goal), the composer ANNOTATES it — NOT mutating the task (only-people-decide), but attaching context + the concrete next step as an INSIGHT citing the source. Enrichment is engine-free (insight kind + existing grant), verifiable (was the task actionable before? is it now?), and COMPOUNDS (rich tasks make a richer graph, so real outcomes compose better later). (4) COMPOSE an outcome only when the arrival + its situated graph imply a GOAL LARGER THAN ANY SINGLE EVIDENCE ROW — the bright-line that refuses wrappers. Enrich → link → compose is one spectrum; the agent advances a specific arrival as far as the evidence honestly supports, no further. Only genuine outcomes reach the feed; thin work becomes enrichment. First cut is Jules-side (SITTING.md/formula/skill/driver), no engine change; hard engine guards + a dedicated annotation kind are follow-ups if it proves out.

### sitting-floor-one-new-outcome

*Superseded by no-floor-advance-one-arrival above; kept for the history it refers to.*

THE SITTING'S FLOOR (owner's ruling, 2026-08-27): a composer sitting NEVER has no work. Whatever else is owed, every sitting surfaces at least ONE NEW OUTCOME the house does not yet hold — found by digging: evidence rows no outcome or insight has cited yet (tasks, events, media, chore runs, people, values, threads), read in full, and as the house grows, email/Telegram/any source ingested as a kind. 'Nothing was owed' is not a lawful no-op; if the dig honestly finds nothing distinct to stage, the JOURNAL is then mandatory and says what was searched and why nothing honest could be staged. The old rule 'a run that writes nothing is still correct' is retracted. Email and Telegram are not kinds in the house yet (no bead existed 2026-08-27; filed as the ingest gap).

### waymark-iqa-over-declares-how-work-ends

The feed's first real read (waymark-iqa.24/.15/.25) added ONE declaration key and it is the thing to reach for whenever a surface has to tell finishing from giving up: :over {:accomplished #{:done} :let-go #{:skipped}}, or {:field :status :accomplished #{"finished"} :let-go #{"abandoned"}} for a mirror kind whose lifecycle is data. Unspelled = terminal states are endings and all of them count, so nothing moved for kinds that say nothing. It is READ-SIDE ONLY and therefore NOT fingerprinted (the :nav precedent) — proved by an assertion in workqueue10.fingerprint-stability-test that dissoc'ing :over leaves each of the four declaring kinds' hashes byte-identical, so four declarations changed at once with ZERO law revisions at work.kopsa.info. Readers: feed/work-over? (do-now excludes, the archive requires), feed/accomplished? (fuel's deeds), feed/set-aside? (the narrower one — a LET-GO row keeps its tickler), seasons/classify (a let-go landing is not a completion). Two more lessons from the same read: (1) a per-kind SPREAD is composition, not a score — next_actions candidates carry :lane = their place in their own kind's seeded order and the mixer sorts lane-then-hash, which is how thirty-three tasks stopped losing to two hundred media rows; a recipe entry may also name :kinds to dedicate a line, and workqueue10.main/feed-recipe gives the queue two of do-now's five slots. (2) feed/ctx-opts was a hand-built twin of router/render-opts missing the :probe-reads hooks, so card verbs were the optimistic advertisement while the row's screen showed the honest set — any future document route will make this mistake.

### waymark-jfv-20-within-the-ctx-knows-whose-hand

waymark-jfv.20 grew ONE framework seam and it is the thing to reach for whenever a door must open for another kind's own handler and for nobody's hand: (:within ctx) is the {:kind :action} of the write a nested ctx :invoke / ctx :create was opened INSIDE of (invoke/make-ctx opts :self/:within — invoke-in-tx! and create-in-tx! pass :self, the ctx doors hand it down as :within, the deferred :on-create births too), nil at the wire, on the render probe and in every rehearsal. A guard declares :reads [:within]; usability/declaration-reads and scenario/offline-reads both list it, so it is a declaration read (effort-honesty silent) and CHECK-TIER (the tier serves nil, which is the same answer a client's knock gets). First reader: composition_request/answered-by-a-composition admits only outcome.create — the outcome's :on-create invokes composition_request.answer {outcome_id (:id row)} BEFORE its own insert (the row id is minted ahead of the hook, and the hook's ctx keeps :invoke while :create defers), so the request reads answered in the same transaction and a second citation meets a STATE. Two more findings: (1) a deferred scenario attempted AS AN AGENT gets the router's 404 (no leash — waymark-zs9), so a create-door principal wall on a kind whose other create guards read rows cannot be a scenario; prove it by a leashed deftest + a pack claim instead. (2) a document field spelled the same as an action's input field makes the door read as an EDIT to the battery (edit implies a fence) — name the stamp for what it is (answered_by) and keep the input the ref (outcome_id, typed :waymark/ref; dangling refs are a guard's business, never the engine's).

### waymark10-check-closure-judges-action-doors-only-create

waymark10 check-closure judges ACTION doors only (create-guards are outside it): a guard that :judges a free-text input on an action must either carry :open — which usability/effort-honesty then re-raises as a warning unless the guard's :reads names :storage or a kind keyword — or the field must carry one of checks/constraint-keys (enum/const/format/bounds/minLength/maxLength/pattern) or an :x-display :widget; minItems on a vector does NOT count. Also: the conformance walker is a :system actor, so a kind whose create door refuses :system cannot have deferred ACTION scenarios (run-scenario stages the :row through the create door as the walker) — keep such a kind's action-door guards to :principal reads so its scenarios stay check-tier.
